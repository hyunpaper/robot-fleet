# Robot Fleet

공장 물류 로봇(AMR) 군집을 운영하기 위한 관제 플랫폼.
경로 계획부터 충돌 회피, 교착 해소까지 로봇 운행의 판단을 한곳에서 내리고,
그 과정에서 쌓인 운행 데이터로 "이 공장에 로봇은 몇 대가 적정한가"에 수치로 답한다.

관제 서버는 매 틱 전체 로봇의 이동 요청을 한 번에 받아 승인한다.
데이터 소스는 가상 공장 시뮬레이터이므로, 로봇 대수와 틱 주기만 조정하면
실제 설비 없이도 초당 수만 건 규모까지 부하를 재현할 수 있다.

### 교착 대응 자동화

교착이 발생하면 AI 에이전트가 당시의 대기 그래프, 로봇 궤적, 맵 구조를 근거로 원인을 진단하고
경로 정책이나 레이아웃 수정안을 코드 변경으로 제시한다.
관리자는 진단 보고서와 변경 내역을 검토해 승인만 하면 되고, 이후 검증과 배포는 파이프라인이 이어서 처리한다.
같은 유형의 교착이 반복될수록 대응 시간은 짧아지고, 판단의 근거는 모두 기록으로 남는다.

## 현재 상태

| 단계 | 내용 | 상태 |
|---|---|---|
| M1 | 맵 로드·검증, A* 경로 탐색(회전 비용 포함), 단일 로봇 시뮬레이션 | 완료 |
| M2 | 다중 로봇, 충돌 회피, 교착 탐지·해소 | 진행 예정 |
| M3 | Ingest API + RabbitMQ + Worker로 이벤트 파이프라인 분리 | |
| M4 | 락·상태·멱등 키를 Redis로 이전, 관제 서버 다중 인스턴스 | |
| M5 | k3s 배포, nginx ingress, 스케일 아웃 | |
| M6 | Prometheus + Grafana, 실시간 관제 화면 | |
| M7 | 실험: 로봇 수별 처리량, 회피 전략·우선순위 정책 비교 | |
| M8 | 장애 주입: pod 강제 종료, 브로커 재시작, 네트워크 지연 | |
| M9 | 교착 분석 에이전트: 원인 진단, 수정안 생성, 승인 후 자동 배포 | |

## 구조

```
robot-fleet/
├── src/
│   ├── Shared/            좌표, 맵 로더·검증, 도메인 모델
│   ├── FleetController/   A* 경로 계획, 이동 승인
│   └── Simulator/         틱 루프, 로봇 이동, 콘솔 출력
├── tests/                 xUnit 테스트 (Shared / FleetController / Simulator)
├── tools/                 트레이스 내보내기, GIF 렌더러
├── maps/
│   ├── factory-a.json     60×40 공장 맵
│   └── test-corridor.json 9×7 테스트 맵 (1칸 통로)
└── docs/                  설계 문서
```

이후 단계에서 `IngestApi`, `EventWorker`, `QueryApi`, `deploy/`, `loadtest/`가 추가된다.

## Core Business

| 과제 | 문제 | 해결 |
|---|---|---|
| **틱 단위 배치 판정** | 로봇 200대가 각자 이동 승인을 요청하면 HTTP 왕복만으로 100ms 틱 예산을 넘긴다 | 틱마다 전체 요청을 한 번에 받아 우선순위순으로 판정하고, 통과분은 Redis Lua 한 번으로 일괄 잠금. 로봇 수가 늘어도 왕복 횟수는 그대로 |
| **충돌 회피** | 같은 칸 진입, 1칸 통로 마주보기(자리 맞바꿈), 정지한 로봇 추종 | 현재 칸과 다음 칸을 함께 잠그는 2칸 선점. 맞바꿈은 후순위 로봇을 거부 |
| **우선순위와 기아 방지** | 목적지가 가까운 로봇만 우선하면 먼 작업은 끝나지 않는다 | 대기 시간, 잔여 거리, 작업 긴급도를 합산한 점수. 오래 기다릴수록 순위가 올라간다 |
| **교착 탐지·해소** | 분산 락 방식은 순환 대기가 생긴다 | 대기 그래프에서 순환을 찾아 양보 비용이 가장 낮은 로봇을 회피 지점으로 후퇴. 다중 인스턴스가 같은 교착을 중복 처리하지 않도록 해소 자체에도 락 |
| **락 만료** | 실시간 TTL은 배속을 바꾸면 의미가 달라진다 | 락 값에 틱을 기록해 20틱 지나면 논리 만료. 실시간 TTL은 시뮬레이터가 멈췄을 때의 안전망 |
| **이벤트 순서 보장** | 작업 완료가 시작보다 먼저 처리되면 상태가 깨진다 | `robotId` 기준 consistent hash 16파티션, 파티션마다 single active consumer. 워커 증감 시 명부 기반 재배정 |
| **멱등 처리** | 큐 발행 실패 후 재전송된 이벤트가 중복으로 버려지거나 두 번 집계된다 | 이벤트 ID를 `{batchId}/{index}`로 고정. Ingest는 pending/done 2단계 키, Worker는 테이블별 유니크 제약으로 2차 방어 |
| **상태 유실 복구** | Redis가 비워지면 모든 셀 락이 사라진다 | 세대(epoch) 키로 유실을 감지하고, 시뮬레이터가 전 로봇의 현재 위치로 락을 다시 세운 뒤 재개 |
| **경로 계획** | 최단 거리 경로가 회전이 많아 실제로는 더 느리다 | 탐색 상태를 (x, y, 방향)으로 두고 회전 비용을 포함한 A*. 60×40 맵 기준 1회 0.15ms |
| **효율 측정** | "안 움직인 시간"만으로는 원인을 알 수 없다 | 시간을 이동·작업·대기·유휴로 분해. 대기가 높으면 통로, 유휴가 높으면 로봇 수가 병목 |
