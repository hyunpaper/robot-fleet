# 04. 경로 탐색과 충돌 회피

## 경로 탐색 — A*

### 비용 함수

```
f(n) = g(n) + h(n)

g(n) = 시작점부터 n까지 실제 비용
h(n) = n부터 목적지까지 추정 비용 (맨해튼 거리)
```

4방향 이동이므로 휴리스틱은 **맨해튼 거리**를 쓴다.

```csharp
int Heuristic(Point a, Point b)
    => Math.Abs(a.X - b.X) + Math.Abs(a.Y - b.Y);
```

### 회전 비용 포함

직진 1칸과 회전 후 1칸은 소요 시간이 다르다.

```
이동 비용 = 1.0
회전 비용 = 0.5 (90도당)      (설정: turn_cost)
```

같은 거리라면 **회전이 적은 경로를 선호**하게 된다. 이걸 넣지 않으면
로봇이 지그재그로 움직여 실제 소요 시간이 늘어난다.

따라서 탐색 노드는 `(x, y)`가 아니라 **`(x, y, heading)`** 이다.
같은 칸이라도 바라보는 방향이 다르면 다른 상태로 취급한다.

```csharp
readonly record struct Node(short X, short Y, byte Heading);
```

### 혼잡 가중치 (M7 실험)

과거 혼잡 데이터를 비용에 반영하면 **붐비는 길을 피해 간다.**

```
비용 = 기본 이동 비용 × (1 + α × 혼잡도)
```

- `α = 0` → 최단 경로만 (기본)
- `α > 0` → 돌아가더라도 막히지 않는 길

α는 설정 `congestion_alpha`다("## 설정값").

**실험 거리** — α를 바꿔 가며 처리량이 어떻게 변하는지 측정한다.
직관적으로는 혼잡 회피가 좋을 것 같지만, 모든 로봇이 같은 우회로로 몰리면
오히려 나빠질 수 있다.

### 성능

맵 60×40 = 2400칸, 방향 4개 → 최대 9600 노드.
A* 한 번에 1~5ms. 로봇 200대가 동시에 재계획하면 부담이 되므로

- 경로 캐시 (출발·목적지 쌍 기준, 맵이 바뀌지 않으면 재사용)
- 재계획 쿨다운 (같은 로봇이 100ms 내 재계획 금지)
- 계획은 FleetController에서만 수행 (Simulator는 요청만). M1에서는 FleetController 라이브러리를
  Simulator 프로세스 안에서 직접 호출한다 (06 참조) — M3에서 HTTP로 분리해도 인터페이스는 같다

## 충돌 유형

### 1. 정점 충돌 (Vertex Conflict)

같은 시각, 같은 칸에 둘 이상이 진입하려 함.

```
시각 t       시각 t+1
R1 → [ ]     R1 → [X] ← R2     둘 다 X로 가려 함
R2 → [ ]
```

**해결** — 우선순위가 높은 쪽이 진입, 낮은 쪽은 대기.

### 2. 교차 충돌 (Edge / Swap Conflict)

서로 자리를 맞바꾸려 함. **1칸 통로에서 마주봤을 때.**

```
시각 t:     [R1][R2]
시각 t+1:   [R2][R1]     ← 불가능. 서로 통과할 수 없음
```

**해결** — 단순 대기로는 풀리지 않는다. 둘 다 상대를 기다리므로 영원히 멈춘다.
→ 한쪽이 **갈림길까지 후퇴**해서 비켜 줘야 한다.

```
   [ ][R1][R2][ ]
    ↑ 여기가 비어 있으면
   [R1][ ][R2][ ]   R1이 후퇴
   [R1][R2][ ][ ]   R2가 통과
```

후퇴할 곳이 없으면 더 먼 곳까지 되돌아가야 한다. **이 로직이 가장 복잡하다.**

### 3. 추종 충돌 (Following Conflict)

앞 로봇이 멈춰 있는데 뒤에서 따라붙음. 실제로는 충돌이 아니라 **지연**이다.

```
[R1(waiting)][R2 → ]
```

**해결** — R2도 대기. 다만 R1의 대기가 길어지면 R2는 우회를 검토한다.

## 회피 전략 두 가지

### 전략 A — 시공간 예약 (Space-Time Reservation)

경로를 계획할 때 **`(칸, 시각)` 단위로 미리 예약**한다.

```
R1 경로:  t=0 (3,5) → t=1 (4,5) → t=2 (5,5)
          예약: [3,5,t0] [4,5,t1] [5,5,t2]

R2 계획 시 [4,5,t1]이 이미 예약됨 → 그 시각을 피해 계획
```

| 장점 | 단점 |
|---|---|
| 충돌이 원천 차단됨 | 예약 테이블이 커짐 (칸 × 시간축) |
| 교착이 발생하지 않음 | 지연이 생기면 전체 예약이 어긋나 재계획 폭증 |
| | 시뮬레이션 시각과 실제 시각이 어긋나면 무용지물 |

**적용 시점** — M7 실험에서 비교군으로 구현.

### 전략 B — 분산 락 (기본 채택)

다음 한두 칸만 잠그고 전진한다.

```
1. 로봇이 다음 칸 (x,y) 진입 시도 → 그 틱의 배치 요청에 포함 (01 "틱 단위 배치 이동 판정 API")
2. FleetController: 배치 내 정렬·순차 판정 후 커밋 Lua 1회로 맵 해시의 c:{x}:{y} 필드 일괄 점유
   값 = "{robotId}:{tick}", 칸별 만료 없음 — 해제는 명시적으로만 (01 "칸 점유", 08 §4)
3. 성공 → 이동
4. 실패 → 대기 또는 재계획
5. 이동 완료 후 이전 칸 락 해제
```

| 장점 | 단점 |
|---|---|
| 가볍고 확장성 좋음 | **교착이 발생한다** |
| 지연에 강함 (예약 틀어질 일 없음) | 별도 탐지 로직 필요 |
| 상태가 Redis에 있어 다중 pod 가능 | |

**기본 전략으로 채택한다.** 교착 처리가 과제로 남지만, 그 과제를 푸는 것이
이 프로젝트의 핵심 가치다.

#### 2칸 선점이 필요한 이유

다음 1칸만 잠그면 교차 충돌을 막을 수 없다.

```
[R1][R2]
R1이 R2 자리를 잠그려 하고, R2가 R1 자리를 잠그려 함
→ 둘 다 실패하거나 둘 다 성공 (타이밍에 따라)
```

**현재 칸은 계속 잠근 채로** 다음 칸을 추가로 잠근다. 이동 완료 후 이전 칸 해제.
이렇게 하면 R2가 R1의 현재 칸을 잠글 수 없어 교차 충돌이 방지된다.

## 우선순위 정책

충돌 시 누가 양보하는가. 여러 안을 두고 **실험으로 비교한다.**

| 정책 | 규칙 | 예상 특성 |
|---|---|---|
| **FIFO** | 먼저 요청한 쪽 | 단순. 기아(starvation) 가능 |
| **잔여 거리** | 목적지가 가까운 쪽 우선 | 평균 완료 시간 개선 |
| **대기 시간** | 오래 기다린 쪽 우선 | 기아 방지. 전체 효율은 낮을 수 있음 |
| **작업 우선순위** | 긴급 작업 우선 | 현실적 |
| **복합** | 대기시간 가중 + 잔여거리 | |

기본은 **대기 시간 가중 복합**으로 간다.

```csharp
double Priority(Robot r)
    => r.WaitMs * 0.01            // 오래 기다릴수록 ↑     (설정: priority.wait_weight)
     + (100 - r.RemainingSteps)   // 목적지 가까울수록 ↑   (설정: priority.distance_weight, 기본 1.0)
     + r.TaskPriority * 50;       // 긴급 작업            (설정: priority.task_priority_weight)
```

**기아 방지가 중요하다.** 순수 "가까운 쪽 우선"이면 먼 거리 작업을 맡은 로봇이
계속 밀려 영원히 도착하지 못할 수 있다. 대기 시간을 가중치에 넣어 막는다.

## 교착 탐지와 해소

### 대기 그래프

로봇이 대기할 때 "누구를 기다리는지"를 기록한다.

```
R1 → R2    (R1이 R2가 비켜 주길 기다림)
R2 → R3
R3 → R1    ← 순환! 교착
```

**탐지 방법** — 대기 관계를 방향 그래프로 보고 **순환을 찾는다**.

```csharp
// Redis에 대기 관계 저장
// wait:{mapId}:{robotId} → "{blockedByRobotId}:{tick}"   TTL 5s

bool DetectCycle(string startRobot, out List<string> cycle)
{
    var visited = new HashSet<string>();
    var path = new List<string>();
    var current = startRobot;

    while (current != null)
    {
        if (!visited.Add(current))        // 이미 방문 → 순환
        {
            var idx = path.IndexOf(current);
            cycle = path.Skip(idx).ToList();
            return true;
        }
        path.Add(current);
        current = redis.Get($"wait:{current}");
    }
    cycle = null;
    return false;
}
```

체인 길이는 보통 2~4다. 전체 그래프를 순회할 필요 없이
**대기가 일정 시간(예: 1초, 설정: `deadlock_detect_wait_ms`) 이상 지속된 로봇에서만** 탐지를 시작한다.

### 해소 — 양보(Yield)

순환에서 **한 대를 골라 후퇴**시킨다.

```
선정 기준: 양보 비용이 가장 낮은 로봇

  yieldCost = yield_cost.distance_weight × (회피 지점까지 거리)
            + yield_cost.priority_weight × (1 / 작업 우선순위)
```

두 항의 비중을 바꾸면 "가까운 로봇을 양보시킨다" ↔ "덜 급한 로봇을 양보시킨다" 사이를 움직인다.
기본값은 둘 다 1.0이고, 기존 서술("가까운 회피 지점까지의 거리 + 작업 우선순위 역수")과 동일한 동작이다.

**회피 지점(Yield Point)** = 현재 경로에서 벗어날 수 있는 칸.
교차로, 폭 2칸 이상 통로, 빈 Parking 등.

```csharp
Point? FindYieldPoint(Robot robot, int maxDistance = 5)   // 설정: yield_search_max_distance
{
    // 현재 위치에서 BFS로 탐색
    // 조건: 통행 가능 + 미점유 + 다른 로봇의 계획 경로가 아님
    // 가장 가까운 곳 반환
}
```

양보 지점을 찾지 못하면 **탐색 범위를 넓히고**, 그래도 없으면
**작업을 실패시키지 않고 대기를 유지한 채 `deadlock_detect_wait_ms` 간격으로 재시도**한다(다음 시도에서 다른 로봇을 양보시킬 수 있다).
장기 미해소는 **경보**로 알린다(게이지 `fleet_deadlock_unresolved_active`·`fleet_deadlock_unresolved_oldest_seconds` — 맵 설계 문제 신호).
작업 실패 시간 상한은 두지 않는다(사용자 결정, 07). 재시도는 재계획 상한에 세지 않고, 실제 양보 경로를 심는 순간만 센다.

### 해소 절차

```
1. 교착 감지 (대기 1초 초과 + 순환 발견) — 배치 판정 6단계 안에서 실행
2. 교착 해소 락 획득 (아래) — 실패하면 기존 해소 결과를 읽어 그대로 적용
3. 양보 로봇 선정, 락 값에 기록
4. 배치 응답에 deadlock 항목으로 반환 → Simulator가 DeadlockDetected 발행, 양보 로봇에 회피 지점 이동 명령
5. 회피 완료 후 나머지 로봇 재계획
6. 양보 로봇도 원래 작업 재계획
```

### 교착 해소 락 — 같은 교착을 두 pod가 동시에 풀지 않게

FleetController pod가 여럿이면 같은 순환을 둘이 동시에 발견해 **서로 다른 로봇을 양보**시킬 수 있다.
두 대가 동시에 후퇴하면 교착은 풀리지만 손실이 2배이고, 최악에는 후퇴 경로가 또 교차한다.

```
키:   deadlock:resolve:{mapId}:{cycleKey}
      cycleKey = 순환에 포함된 robotId를 정렬해 '|'로 이은 문자열   예) "R-007|R-012|R-034"
값:   "{resolverPod}:{tick}:{yieldRobotId}:{yieldToX},{yieldToY}"
획득: SET key value NX PX {50틱 환산 실시간}
```

| 규칙 | 근거 |
|---|---|
| 키는 **정렬된 robotId 집합** | 순환을 어느 로봇에서 시작해 탐색했든(R-012→R-034→R-007 / R-034→R-007→R-012) 같은 키가 나와야 한다 |
| `SET NX` 실패 시 **값을 읽어 같은 결정을 적용** | 두 번째 발견자는 새로 결정하지 않는다. 양보 로봇·회피 지점이 한 가지로 수렴 |
| 양보 로봇에 `robot:yielding:{robotId}` 표시 (TTL 50틱) | 부분 집합 순환(R-007|R-012)을 다른 pod가 따로 찾아내도, 이미 양보 중인 로봇이 끼어 있으면 **새 해소를 시작하지 않는다** |
| TTL 50틱 (설정: `deadlock_resolve_ttl_ticks`) | 후퇴 최대 5칸 × 10틱/칸. 그 안에 안 풀리면 다시 탐지되어 새 해소를 시작. 탐색 거리와의 연동 제약은 "## 설정값" |
| 해소 완료(양보 로봇이 회피 지점 도착) 시 락 삭제 | 같은 로봇들이 다시 교착에 빠지면 새 해소가 가능해야 한다 |

> **배치 API 덕분에 경쟁은 드물다.** 한 틱의 배치는 pod 하나가 통째로 처리하므로
> 같은 틱에 두 pod가 같은 교착을 보는 일은 구조적으로 없다. 경쟁이 생기는 경우는
> (a) 배치 타임아웃 후 Simulator가 재전송해 다른 pod가 같은 틱을 다시 처리할 때,
> (b) M8 이후 백그라운드 탐지기를 따로 둘 때다. 락은 그 두 경우를 위한 보험이다.
> 보험치고는 싸다 — 교착은 드물고, 키 하나에 `SET NX` 한 번이다.

> **M4 구현** — 대기 그래프 · 해소 락 · 양보 표시는 별도 키가 아니라 맵 해시의 `wg` · `dl` · `yl` 필드이고,
> 판정 기록과 같은 커밋 Lua에서만 쓴다. (a)는 재전송 기록 반환이 막아 재탐지 자체가 없고,
> (b)를 도입하려면 같은 커밋 조건을 거쳐야 한다. 위 규칙(정렬 키, 기존 결정 재사용, 50틱)은 그대로다. → 08 §4

> **run 전환 시 맵 해시 초기화 + epoch 증가가 필요하다.** 칸 점유는 "해제는 명시적으로만"이라 TTL로
> 사라지지 않는다(맵 키 TTL 30초는 버려진 맵 정리용). run을 바꾸면서 지우지 않으면 이전 run이 점유한
> 칸이 그대로 남아 새 run이 즉시 교착에 빠진다. run 전환을 epoch 증가로 묶으면 전환 중 도착한 옛 판정도
> 체인 검사(08)에서 자연히 거부된다. 전환 절차는 02 "run 관리".

## 재계획 트리거

| 상황 | 동작 |
|---|---|
| 다음 칸 점유 (일시적) | 대기 (재계획 안 함) |
| 대기 500ms 초과 (설정: `replan_wait_threshold_ms`) | 재계획 시도 |
| 교착 감지 | 양보 후 재계획 |
| 경로상 칸이 장기 점유 | 재계획 |
| 맵 변경 (설비 추가 등) | 전체 재계획 |

**대기 즉시 재계획하지 않는 이유** — 앞 로봇이 곧 지나갈 수 있는데
매번 재계획하면 CPU 낭비이고, 모든 로봇이 동시에 우회로로 몰려
**혼잡이 다른 곳으로 옮겨 갈 뿐**이다.

### 재계획 폭주 방지

```
- 로봇당 쿨다운 100ms                              (설정: replan_cooldown_ms)
- 같은 작업에서 재계획 5회 초과 → 작업 실패 처리     (설정: replan_max_per_task)
- 전체 재계획 비율이 임계치 초과 시 알림 (맵/로봇수 설계 문제)
```

## 중앙 집중 vs 분산

### M1~M5 — 중앙 집중

FleetController가 모든 판단을 한다.

| | |
|---|---|
| 장점 | 전역 정보로 최적 판단. 교착 탐지가 쉬움 |
| 단점 | 단일 병목. 로봇 수가 늘면 처리 한계 |

### M7+ — 부분 분산 (실험)

로봇이 자율적으로 판단하고 충돌 시에만 중앙에 문의.

| | |
|---|---|
| 장점 | 확장성. 중앙 부하 감소 |
| 단점 | 전역 최적이 아님. 교착 탐지가 어려움 |

**비교 실험 대상.** 로봇 수를 늘려 가며 두 방식의 처리량과
판단 지연(p99)을 비교하면, "언제 분산이 필요한가"에 데이터로 답할 수 있다.

## 설정값

알고리즘 동작을 바꾸는 값은 코드 상수가 아니라 설정으로 둔다.
M7 실험(05)과 M9 교착 분석 에이전트(아래)가 같은 축을 조작하므로 한곳에 모은다.
기본값은 위 본문의 값 그대로다.

| # | 설정 키 | 기본값 | 허용 범위 | 1회 변경 상한 | 본문 | 영향 지표 (05) |
|---|---|---|---|---|---|---|
| 1 | `congestion_alpha` | 0 | 0 ~ 2.0 | ±0.3 | 경로 탐색 — 혼잡 가중치 | 경로 효율, 혼잡 손실률 |
| 2 | `turn_cost` | 0.5 | 0 ~ 2.0 | ±0.25 | 경로 탐색 — 회전 비용 | 경로 효율, 리드타임 |
| 3 | `priority.wait_weight` | 0.01 | 0 ~ 0.1 | ±0.01 | 우선순위 정책 | 리드타임 **p99**, 작업 실패율 |
| 4 | `priority.distance_weight` | 1.0 | 0 ~ 3.0 | ±0.5 | 우선순위 정책 | 평균 리드타임 |
| 5 | `priority.task_priority_weight` | 50 | 0 ~ 200 | ±25 | 우선순위 정책 | 긴급 작업 리드타임 |
| 6 | `replan_wait_threshold_ms` | 500 | 200 ~ 2000 | ±250 | 재계획 트리거 | 재계획률, 혼잡 손실률 |
| 7 | `replan_cooldown_ms` | 100 | 50 ~ 1000 | ±100 | 재계획 폭주 방지 | 재계획률, 판단 p99 |
| 8 | `replan_max_per_task` | 5 | 3 ~ 10 | ±2 | 재계획 폭주 방지 | 작업 실패율 |
| 9 | `deadlock_detect_wait_ms` | 1000 | 500 ~ 3000 | ±500 | 교착 탐지 | 교착 발생률, 해소 시간 |
| 10 | `yield_search_max_distance` | 5 | 3 ~ 15 | ±3 | 해소 — 양보 | 교착 해소 시간, 작업 실패율 |
| 11 | `yield_cost.distance_weight` | 1.0 | 0 ~ 3.0 | ±0.5 | 해소 — 양보 비용 | 교착 해소 시간 |
| 12 | `yield_cost.priority_weight` | 1.0 | 0 ~ 3.0 | ±0.5 | 해소 — 양보 비용 | 긴급 작업 영향 |
| 13 | `deadlock_resolve_ttl_ticks` | 50 | 30 ~ 120 | ±20 | 교착 해소 락 | 재탐지 빈도 |

**연동 제약** — `deadlock_resolve_ttl_ticks >= yield_search_max_distance × 10`.
TTL 50틱의 근거가 "후퇴 최대 5칸 × 10틱/칸"이므로, 탐색 거리를 늘리면 TTL도 함께 늘려야 한다.
그러지 않으면 후퇴가 끝나기 전에 해소 락이 풀려 같은 교착을 다시 해소하려 든다.

> **파생 제약 — 탐색 거리는 한 번에 +2까지만 올라간다.** 10번의 1회 상한은 ±3이지만 13번의 상한이 ±20이라
> `5 → 8`은 TTL 80이 필요한데 `50 → 70`까지만 가능하다. 도달 가능한 단일 변경은 **`5 → 7` + `50 → 70`**이고,
> 더 올리려면 다음 회차에 다시 +2 한다.

> **M9 에이전트가 조작할 수 있는 축이 정확히 이 표다**(아래 등급 A).
> 2칸 선점 · 칸 점유 만료 없음은 안전성 불변식이므로 설정값이 아니다.

### M9 교착 분석 에이전트의 액션 공간

M9는 자유 코드 생성이 아니라 **허용된 파라미터 중 선택 + 근거 제시**다. 이유는 비용이 아니라 **검증 가능성**이다 —
액션이 열거 가능하면 파이프라인이 기계적으로 거르고, 사람은 근거만 읽는다.

| 단계 | 누가 | 산출 |
|---|---|---|
| 1 | **규칙**(기존 탐지 로직 + 이벤트 조회) | 확정된 사실 — `cause_type`, 순환 체인, 칸, 혼잡도, 현재 설정값, 최근 지표, 과거 조치 이력 |
| 2 | **로컬 LLM** | 등급 A 13개 중 무엇을 얼마나 바꿀지 + 근거 |

| `cause_type` | 판정 출처 (03) |
|---|---|
| `cycle_wait` | `DeadlockDetected` + `cycle` |
| `swap_headon` | `ConflictDetected.conflictType == "edge"` |
| `following_delay` | `ConflictDetected.conflictType == "following"` |
| `replan_storm` | `PathReplanned` 수 (재계획 상한) |
| `starvation` | `TaskCompleted` 리드타임 p99 (05) |
| `no_yield_point` | `DeadlockDetected.noYieldRetries > 0`(회피 지점 없이 재시도) |

| 등급 | 범위 | 처리 |
|---|---|---|
| **A** | 위 설정값 13개 | 자동 제안 + PR 생성 |
| **B** | 우선순위 정책 종류 · 회피 전략(분산 락 / 시공간 예약) · 맵 레이아웃(혼잡 히트맵 근거가 있을 때만) · 로봇 수 | 제안만, 사람이 구현 |
| 금지 | 2칸 선점 · 칸 점유 만료 없음 · 해시 체인 워터마크 · 재주장 · `min-replicas-to-write` · `WAIT 1` · 멱등 2단계 · quorum 큐 타입 · 틱 주기 100ms | 선택지에 넣지 않는다 |

| 검증 단계 | 규칙 | 불합격 시 |
|---|---|---|
| 0 | 근거로 든 수치가 1단계 사실에 실재하는가 | 폐기 · 재질의 |
| 1 | **1 PR = 1 파라미터** (연동 제약 쌍만 2개) | PR 없음 |
| 2 | 허용 범위 | PR 없음 |
| 3 | 1회 변경 상한 | 상한으로 잘라 재시도 |
| 4 | 연동 제약 | 13번 동반 변경 요구 |
| 5 | 같은 시드로 시뮬레이션 재실행 | — |
| 6 | **교착 발생률 감소 + 처리량 비악화 + 리드타임 p99 비악화** | 결과를 PR에 붙이고 자동 닫기 |

> 6번이 핵심이다 — "교착은 줄었는데 처리량이 떨어졌다"를 거르지 못하면 에이전트가 시스템을 조금씩 망가뜨린다.
> 05 실험 3의 "평균만 보면 안 된다"에 따라 평균이 아니라 p99를 본다.

## 구현 순서

| 순서 | 내용 | 검증 |
|---|---|---|
| 1 | A* (4방향, 회전 비용 없음) | 로봇 1대가 목적지 도달 |
| 2 | 회전 비용 추가 | 경로가 덜 꺾임 |
| 3 | Redis 셀 락 (1칸) | 로봇 2대가 같은 칸에 안 들어감 |
| 4 | 2칸 선점 | 마주보기에서 겹치지 않음 |
| 5 | 대기 + 우선순위 | 로봇 10대가 막히지 않고 운행 |
| 6 | 교착 탐지 | 1칸 통로 마주보기에서 순환 감지 |
| 7 | 양보 로직 | 교착이 자동 해소됨 |
| 8 | 재계획 정책 | 장기 점유 시 우회 |
| 9 | 혼잡 가중치 (선택) | 붐비는 구역 회피 |

> **6~7단계를 반드시 1칸 통로가 있는 맵에서 검증한다.**
> 넓은 맵에서는 교착이 거의 발생하지 않아 로직이 동작하는지 알 수 없다.
> 의도적으로 좁은 통로와 막다른 길이 있는 테스트 맵을 따로 만든다.
