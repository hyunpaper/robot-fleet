# 09. M3 — 이벤트 파이프라인 분리 (큰 틀)

완료 기준(README): **이벤트가 DB에 적재되고 유실 0.** 이 문서는 범위·경계·증명 방법·테스트 전략을 정하고, 상세 설계는 10이 채웠다. 10이 09를 바꾼 곳(D1~D6)은 리뷰를 거쳐 수용했고, 이 문서는 그 결과에 맞춰져 있다.
08 "구현 작업 분할 M3"의 HA 항목(BatchPublisher · IdemStore · EventBatchSender · Topology · 멱등 테스트)은 그대로 M3에 속한다.

---

## 범위

| 포함 | 제외 |
|---|---|
| Simulator 이벤트 생성 · 틱당 배치 송신 (03 봉투 · `batchId` · 순차 송신) | Redis 기반 Arbiter · FleetController HTTP 분리 (M4) |
| IngestApi — 검증 · 멱등(Redis) · 큐 발행 · 202/503 (01 · 08 §9) | QueryApi · 관제 화면 (M6) |
| RabbitMQ 토폴로지 — exchange 3 · 파티션 큐 48 · DLX/DLQ · `fleet.invalid` (01 · 08 §8, quorum 멤버 1) | 3노드 클러스터 · quorum 멤버 확장 (M5) |
| EventWorker — 파티션 소비 · 배치 INSERT · 증분 집계 · 상태 전이 검증 · DLQ | HPA (M5). 단, 명부 기반 파티션 배정 로직은 M3에서 구현·검증 |
| PostgreSQL 스키마 · 일 단위 파티션 · 마이그레이션 (01) | 보존 정책 자동화(DROP PARTITION 스케줄) |
| Redis 멱등 키 · 워커 명부 (단일 노드) | Sentinel (M5) |
| 최소 메트릭(`/metrics`) · readiness/liveness | Prometheus · Grafana 배포 (M6) |
| 유실 0 대조 도구 | 장애 주입 자동화 (M8) |

> **M3의 Redis는 "있으면 쓰고 없으면 fail-open"이다.** 멱등 키는 유실 허용(07)이고 중복은 워커가 막으므로,
> Redis 없이도 파이프라인이 돌아야 한다. fail-open은 대체 구현이 아니라 **미등록 → null 코드 경로**다. 실행 중 장애는 실제 Redis 구현 안의 분기(오류 · 타임아웃 → Bypass)가 처리한다.

### Simulator 이벤트 — M3에서 실제로 흘러야 하는 것

| 이벤트 | M3 | 근거 |
|---|---|---|
| RobotTelemetry, RobotStatusChanged | **필수** | 지금 Simulator가 아는 사실. 고빈도 큐와 상태 전이 검증의 입력 |
| TaskCreated / Assigned / Started / Completed / Failed | **필수** | "유실 불가" 등급의 대표. 이게 없으면 유실 0 증명이 telemetry(유실 허용)만 재는 꼴이 된다. 작업 생성기(03 포아송)가 아직 없으면 M3에 **최소 생성기**를 포함한다 |
| ConflictDetected | 필수 | InMemoryMoveArbiter 거부 응답을 변환 |
| DeadlockDetected, PathReplanned | 발생하면 발행 | M2 잔여 범위. M3가 생성을 보장하지 않는다 |

## 서비스 경계

```
Simulator ──IEventSink──► EventBatchSender ──HTTP──► IngestApi ──IEventPublisher──► RabbitMQ
                                                         │ IIdemStore (Redis · fail-open)
RabbitMQ ──IPartitionSubscriber──► EventWorker ──IEventStore──► PostgreSQL
                                        │ IPartitionRoster (Redis 명부)
```

| 경계 | 원칙 |
|---|---|
| `src/Shared/Messaging` | 봉투 · 이벤트 DTO · 라우팅 키 규칙 · 토폴로지 선언. **직렬화 가능한 것만**(06 원칙). 5개 서비스가 참조 |
| `src/IngestApi` | 01 그대로: 검증 · 멱등 · 발행 · 즉시 응답. DB를 모른다 |
| `src/EventWorker` | 큐만 소비. 업무 HTTP 없음(관리 포트의 `/metrics` · `/health`만). 핸들러는 이벤트 종류별 순수 함수 + 저장소 인터페이스 |
| `src/Simulator/Events` | 틱 안의 발생 순서로 번호 매김(03), 틱당 배치 1건, 순차 송신 · 재전송 · 버퍼(08 §9). **발행이 틱 예산을 침범하지 않는다** — 송신은 틱 루프 밖 백그라운드, 버퍼 가득 차면 틱 정지 |
| 인프라 접점은 전부 인터페이스 뒤 | `IEventSink` · `IEventPublisher` · `IPartitionSubscriber` · `IIdemStore` · `IEventStore` · `IPartitionRoster`. 구현은 **실제 인프라 하나뿐** — 인메모리 · 가짜 · 우회 구현을 두지 않는다. Redis 미설정은 `IIdemStore?` · `IPartitionRoster?`가 null인 코드 경로(멱등 1단계 생략 · 단일 워커 전 파티션)로 처리한다 |

## 테스트 전략 — 인프라가 닿는 검증은 실제 서버에서만

사용자 결정으로 고정한다(앞으로의 마일스톤에도 같다): **인프라를 흉내 내는 것(인메모리 fake · in-process 파이프라인 · 우회 구현)은 두지 않는다.**
인프라에 닿는 검증은 사용자가 준비한 RabbitMQ · Redis · PostgreSQL 서버에 붙는 통합 테스트로만 한다. 로컬에서 항상 도는 것은 인프라와 무관한 순수 로직 테스트뿐이다.

| 층 | 대상 | 인프라 | 실행 조건 |
|---|---|---|---|
| **순수 로직** | 계약 직렬화 · 라우팅 키 · 토폴로지 명세 · 상태 전이 표, 생성기 · 할당기 · 생애주기 · 수집기 순서, 검증(400 사유), 옵션 파싱, 송신 로그 읽기 | 없음 | 항상. `dotnet test` 기본 |
| **통합** | 멱등 Lua · 상태 전이, 발행 확인 · telemetry drop, 송신기 순차 · 재전송 · 로그(실제 Kestrel IngestApi), 워커 배치 · 커밋 뒤 ack · kill 반환 · 독 메시지 · 전이 검증, 명부 배정 · 재배정 순서, 마이그레이션 · 파티션 · `unnest` · `RETURNING`, E2E(송신 → RabbitMQ → 워커 kill · 교대 → PG → Reconcile) | **원격 서버**의 실제 인프라 | 접속 정보가 환경 변수에 있을 때만. 없으면 **skip으로 표시**(실패 아님) |
| **E2E (완료 기준)** | 완료 기준 1~6 | 원격 서버 인프라 + 서비스 프로세스, 이후 M5 k3s | 수동 · 보고서 첨부 |

| 원칙 | 근거 |
|---|---|
| 가짜 인프라 금지 | fake가 실제와 다르게 동작하면 통과가 거짓 안심이 된다. 실제 서버에서 통과한 것만 통과다 |
| 대역 없이 재현할 수 없는 실패(브로커 nack · confirm 타임아웃 · 채널 끊김 · 저장소 일시 오류 · 커밋 직후 예외)는 **M8 실제 장애 주입**으로 검증한다 | 흉내로 "검증했다"고 하지 않는다. 코드 경로는 리뷰로 확인하고, 실행 검증은 M8 |
| 통합 테스트는 `Category=Integration` trait. 접속 정보는 환경 변수(`FLEET_TEST_RABBITMQ` · `FLEET_TEST_REDIS` · `FLEET_TEST_PG`)로 주입, 비어 있으면 skip | "서버 없어서 실패"가 없다. 로컬과 CI가 같은 규칙 |
| **접속 정보 · 비밀번호는 저장소에 넣지 않는다.** 코드 · 설정 파일 · 문서 · 커밋 메시지 어디에도. `appsettings`의 연결 문자열은 빈 값 | 원격 서버가 실제 자산이다 |
| 통합 테스트는 **자기 자원을 스스로 만들고 지운다** — 토폴로지 접두사 · 키 접두사 · 스키마 이름에 실행 id | 공용 서버를 여러 실행이 나눠 쓴다. 남은 자원이 다음 실행을 오염시키면 안 된다 |
| 완료 선언은 **실제 서버에서 통합 · E2E를 돌린 뒤** | 컴파일만 된 통합 테스트는 아직 아무것도 증명하지 않았다 |

## 총괄 결정

| 결정 | 내용 | 근거 |
|---|---|---|
| 최소 작업 생성기 포함 | 03의 포아송 생성 · Station 무작위 출발/목적 · `Idle → Moving → Loading → Moving → Unloading → Idle` 생애주기 | task 이벤트 없이는 M3 완료 기준 1을 증명할 수 없다 |
| 스키마는 SQL 파일 + 기동 시 적용 | `db/migrations/NNN_*.sql`, EventWorker 기동 시 advisory lock 안에서 순서대로 적용(이력 · 체크섬). ORM 마이그레이션 금지 | 01 스키마가 이미 SQL이고 파티션 DDL은 ORM이 못 다룬다 |
| 파티션 사전 생성 | EventWorker가 당일 + 익일(UTC) 파티션을 기동 시와 **매시** 만들고, DEFAULT 파티션을 둔다 | 파티션 없는 날짜의 INSERT는 실패 = 유실. 자정 타이머 하나는 재시작 중이면 놓친다 (10 D3) |
| 메시징 라이브러리 | **`RabbitMQ.Client` 직접 사용.** README 스택 표 수정 | 01 토폴로지 7항목 중 처리 완료 순서 ack와 "DB 일시 오류 시 nack 없는 재시도"를 MassTransit이 못 맞추고, `_error` 큐 재발행이 08 §8의 `x-delivery-limit` · DLX를 무력화한다 (10 §3 비교표). 토폴로지가 라이브러리보다 우선 |
| 집계 멱등은 원본 INSERT의 `RETURNING` | 같은 트랜잭션에서 `ON CONFLICT DO NOTHING RETURNING`으로 **새로 들어간 행만** 집계. Redis `metrics_applied` 집합 폐지 | M3의 Redis는 선택이고, 집합과 집계를 한 트랜잭션에 묶는 쪽이 정확하다 (10 D4) |
| `tickMs`는 봉투에 싣는다 | 배치 봉투에 `tickMs`, Ingest가 항목 봉투로 복사. 워커 설정 `Fleet:TickMs` 폐지 | 워커 설정과 Simulator `--tick`을 사람이 맞추는 구조는 틀어지면 시간 분해가 조용히 왜곡된다. 03 공통 봉투에 필드 하나 추가 |
| 대조 도구 경로 `src/Reconcile` | `tools/`는 GIF 생성 도구용으로 저장소에서 제외됐다 | 완료 기준 증명 도구는 저장소에 있어야 한다. Simulator와 같은 콘솔 프로젝트 자리 |
| 가짜 인프라 금지 (사용자 확정) | 인메모리 · in-process · 우회 구현 없음. 인프라에 닿는 검증은 실제 서버 통합 테스트만 | 위 "테스트 전략". 이후 마일스톤에도 같은 원칙 |
| 명부 기반 파티션 배정은 M3 | 워커 2대 로컬 실행으로 재배정 순서(새 몫 구독 → 옛 몫 취소)와 순서 유지를 검증 | HPA 시연은 M5지만 정확성은 M3에서 |
| 워커는 파티션 단위 배치 | 파티션별로 N건 또는 T ms 창으로 모아 INSERT, 처리 완료 순서대로 ack | 01 "개별 INSERT 금지" + 순서 유지 |
| 서비스마다 `/metrics` · `/health/live` · `/health/ready` | 08 메트릭 표의 Ingest · 송신기 항목 + 워커 처리 · 적체 · invalid · DLQ 카운터 | 완료 기준 2~6의 출처 |

## 리뷰 승인 조건

1. 완료 기준 1~7 각각 "어느 코드 · 어느 테스트 · 어느 스크립트"가 증명하는지 표로 대응된다.
2. 멱등(08 §9) · 순서(01 파티션 · SAC · 명부) · 배치 ack 규칙이 통합 테스트 목록에 **행 단위로** 있다. 실제 서버에서 재현되는 실패(워커 kill 재전달 · Redis 없음 · 독 메시지)는 포함하고, 대역이 필요한 실패(confirm nack · 타임아웃 · 저장소 일시 오류)는 M8 장애 주입 항목으로 이관 목록에 있다.
3. 인프라 구현이 하나뿐이고(가짜 없음), 통합 테스트가 접속 정보 없으면 skip(실패 아님)으로 표시되며, 자원 격리와 정리가 있다. 접속 정보가 저장소 어디에도 없다.
4. Simulator 송신이 틱 루프를 막지 않는 구조이고, 버퍼 상한과 틱 정지 조건이 명시된다.
5. 파티션 사전 생성 · 마이그레이션 적용 순서 · 기동 시 토폴로지 선언 — "처음 띄울 때" 경로가 빠짐없이 있다.
6. 메시징 라이브러리 선택에 01 토폴로지 항목별 가능/불가 근거가 있다.
7. 설정 값마다 근거 한 줄. 측정으로 정할 값은 "M3 측정"으로 표시.
8. 작업 분할이 핵심/단순으로 나뉘고 묶음 간 파일 충돌이 없다.
9. 문서 톤: 표 + 짧은 근거 + `>` 강조.

## 사용자 확인 필요

| 쟁점 | 총괄 입장 |
|---|---|
| 통합 테스트 서버 — 접속 정보 전달 시점 · 방식 | 서버 준비 전에는 순수 로직 테스트까지. 통합 · E2E는 접속 정보를 받은 뒤. 완료 선언은 E2E까지. 접속 정보는 환경 변수로만 받고 저장소에 남기지 않는다 |
| 원격 서버의 RabbitMQ 버전 · 플러그인 | consistent-hash exchange 플러그인과 quorum queue가 켜져 있어야 한다(3.13+ 권장). 준비 시 확인 요청 |
| M2 잔여(교착 탐지 · 해소)와 M3 순서 | M3를 먼저 간다. 파이프라인은 교착 이벤트가 없어도 완성되고, M2 잔여는 M3 위에서 DeadlockDetected를 흘려보내며 검증하는 편이 낫다 |
| 최소 작업 생성기를 M3에 포함 | 포함 (위 총괄 결정). M2 범위라고 보면 M2 잔여로 옮길 수 있으나 M3 완료 기준 1이 그에 묶인다 |
