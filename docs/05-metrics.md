# 05. 지표와 실험

## 시간 분해

모든 효율 지표의 출발점. 로봇의 시간을 네 가지로 나눈다.

```
전체 시간 = 이동(Move) + 작업(Work) + 대기(Wait) + 유휴(Idle)
```

| 구분 | 상태 | 의미 | 개선 방향 |
|---|---|---|---|
| **Move** | Moving | 실제 이동 | 경로 최적화 |
| **Work** | Loading / Unloading | 적재·하역 | 고정값 (설비 성능) |
| **Wait** | Waiting | **충돌 회피로 멈춤** | **혼잡 해소** |
| **Idle** | Idle | 할 일 없음 | 작업 할당 |

> **Wait와 Idle을 반드시 구분한다.** 둘 다 "안 움직이는 시간"이지만 원인과 처방이 정반대다.
> - Idle이 높다 → 로봇이 과잉이거나 작업 발생이 적음 → **로봇을 줄여야 함**
> - Wait가 높다 → 길이 막힘 → **로봇을 줄이거나 통로를 넓혀야 함**
>
> 이 둘을 합쳐서 "비가동"으로 묶으면 아무 판단도 할 수 없다.

---

## 로봇별 지표

| 지표 | 계산식 | 해석 |
|---|---|---|
| 가동률 | `(Move + Work) / 전체` | 실제로 일한 비율 |
| **혼잡 손실률** | `Wait / 전체` | 막혀서 버린 시간 |
| 유휴율 | `Idle / 전체` | 놀고 있던 비율 |
| 처리량 | `완료 작업 수 / 시간` | |
| 경로 효율 | `계획 거리 / 실제 이동 거리` | 1에 가까울수록 좋음 |
| 평균 작업 시간 | `Σ(완료 - 배정) / 건수` | |
| 재계획률 | `재계획 횟수 / 작업 수` | 높으면 혼잡 심함 |

### 경로 효율이 중요한 이유

```
계획 19칸 → 실제 23칸  →  효율 0.83
```

0.83이면 **17%를 우회에 썼다**는 뜻이다. 이 값이 로봇 수에 따라
어떻게 떨어지는지 보면 혼잡의 영향을 직관적으로 알 수 있다.

## 시스템 지표

| 지표 | 계산식 | 용도 |
|---|---|---|
| 전체 처리량 | `시간당 완료 작업 수` | **핵심 지표** |
| 평균 리드타임 | `작업 생성 → 완료 소요 시간` | 사용자 체감 |
| 작업 대기열 길이 | `Pending 작업 수` | 적체 여부 |
| 충돌 발생률 | `충돌 수 / (로봇 수 × 시간)` | 혼잡도 |
| 교착 발생률 | `교착 수 / 시간` | 알고리즘 품질 |
| 교착 해소 시간 | `평균 resolvedMs` | 알고리즘 품질 |
| 작업 실패율 | `Failed / 전체 작업` | |

### 리드타임 분해

```
리드타임 = 대기열 대기 + 로봇 접근 + 적재 + 운반 + 하역
```

어느 구간이 긴지 보면 처방이 갈린다.
- 대기열 대기가 길다 → 로봇 부족
- 로봇 접근이 길다 → 로봇 배치 문제
- 운반이 길다 → 혼잡 또는 거리

## 혼잡 히트맵

맵의 각 칸에 대해 두 값을 누적한다.

| 값 | 의미 |
|---|---|
| **통행량** | 그 칸을 지나간 횟수 |
| **대기 발생** | 그 칸에서 대기가 시작된 횟수 |

```
혼잡도 = 대기 발생 / 통행량
```

통행량만 보면 "주통로가 빨갛다"는 당연한 결과만 나온다.
**통행량 대비 대기 비율**을 봐야 진짜 병목이 드러난다.

- 통행량 많음 + 대기 적음 → 잘 흐르는 간선도로
- 통행량 적음 + 대기 많음 → **구조적 병목** (좁은 통로, 교차로)

Redis에 누적하고 주기적으로 DB에 플러시한다.

```
metrics:heatmap:pass:{mapId}   Hash { "x:y" → count }
metrics:heatmap:wait:{mapId}   Hash { "x:y" → count }
```

## Prometheus 메트릭

### 네이밍 규칙

```
fleet_{대상}_{측정값}_{단위}
```

### 정의

```csharp
// 카운터
fleet_events_received_total{event_type}
fleet_tasks_completed_total{map_id}
fleet_tasks_failed_total{map_id, reason}
fleet_conflicts_total{map_id, conflict_type}
fleet_deadlocks_total{map_id}
fleet_replans_total{map_id, reason}
fleet_tick_overrun_total{map_id}

// 게이지
fleet_robots_active{map_id, status}        // status별 로봇 수
fleet_tasks_pending{map_id}
fleet_queue_depth{queue}
fleet_simulation_tick{map_id}

// 히스토그램
fleet_move_decision_seconds                // 이동 판단 소요
fleet_path_compute_seconds                 // A* 계산 시간
fleet_task_duration_seconds{map_id}        // 작업 완료 시간
fleet_deadlock_resolve_seconds{map_id}
fleet_event_lag_seconds                    // 발생 → 적재 지연
```

### 버킷 설정

```csharp
// 이동 판단 — 1ms ~ 500ms
Histogram.ExponentialBuckets(0.001, 2, 10)

// 작업 완료 — 1s ~ 10min
Histogram.ExponentialBuckets(1, 2, 10)
```

### 주요 쿼리

```promql
# 시간당 처리량
rate(fleet_tasks_completed_total[5m]) * 3600

# 혼잡 손실률 (상태별 로봇 비율)
fleet_robots_active{status="Waiting"}
  / ignoring(status) sum without(status)(fleet_robots_active)

# 이동 판단 p99
histogram_quantile(0.99, rate(fleet_move_decision_seconds_bucket[5m]))

# 큐 적체 증가 추세
deriv(fleet_queue_depth{queue="fleet.telemetry"}[5m])

# 교착 발생 빈도 (시간당)
rate(fleet_deadlocks_total[10m]) * 3600
```

## 실험 설계

포트폴리오의 핵심. **"만들었다"가 아니라 "측정해서 알아냈다"를 보여준다.**

각 실험은 동일 조건에서 변수 하나만 바꾼다.

```
고정: 맵, 작업 발생률(λ), 실행 시간(시뮬레이션 2시간 분량)
반복: 각 조건 3회 → 평균
```

---

### 실험 1 — 로봇 수와 처리량

**가설** — 로봇을 늘리면 처리량이 오르다가 어느 지점부터 떨어진다.

| 변수 | 값 |
|---|---|
| 로봇 수 | 5, 10, 20, 30, 50, 75, 100, 150 |

**측정** — 처리량, 혼잡 손실률, 경로 효율, 평균 리드타임

**예상 결과**

```
처리량
  │        ╭──╮
  │     ╭──╯  ╰──╮
  │  ╭──╯        ╰────
  └────────────────────  로봇 수
            ↑ 최적점
```

로봇을 늘릴수록 Wait 비율이 올라가고, 어느 지점부터 추가 로봇이
기존 로봇을 막아 **전체 처리량이 감소**한다.

**결론으로 쓸 것** — "이 맵에서는 로봇 N대가 최적이며, 그 이상은
혼잡 손실이 추가 처리량을 상쇄한다. 손실률이 X%를 넘는 지점이 변곡점이다."

---

### 실험 2 — 충돌 회피 전략 비교

| 비교군 | 설명 |
|---|---|
| A | 분산 락 + 단순 대기 |
| B | 분산 락 + 교착 양보 |
| C | 시공간 예약 |

**측정** — 처리량, 교착 발생률, 교착 해소 시간, 판단 지연(p99), 작업 실패율

**관전 포인트** — C는 교착이 0이지만 재계획 비용이 커서 로봇 수가 많아지면
오히려 처리량이 떨어질 수 있다. "이론적으로 더 나은 알고리즘이
실제 조건에서는 불리할 수 있다"는 결론이 나오면 그 자체가 좋은 사례다.

---

### 실험 3 — 우선순위 정책

| 비교군 | 규칙 |
|---|---|
| FIFO | 먼저 온 순서 |
| 최단 잔여 | 목적지가 가까운 쪽 |
| 대기 가중 | 오래 기다린 쪽 |
| 복합 | 대기 + 거리 |

**측정** — 평균 리드타임, **리드타임 p99**, 작업 실패율

**관전 포인트** — "최단 잔여"는 평균은 좋지만 p99가 나쁠 것이다
(먼 작업이 계속 밀림 = 기아). **평균만 보면 안 된다**는 사례가 된다.

---

### 실험 4 — 통로 폭 (레이아웃)

| 비교군 | 맵 |
|---|---|
| 좁음 | 모든 통로 1칸 |
| 혼합 | 주통로 2칸, 지선 1칸 |
| 넓음 | 모든 통로 2칸 |

**측정** — 처리량, 교착 발생률, 혼잡 히트맵

넓은 통로는 이동 거리가 늘어나지만(설비 사이가 멀어짐) 혼잡이 줄어든다.
**어느 쪽이 이득인지**를 수치로 보여줄 수 있다.

---

### 실험 5 — 혼잡 가중 경로

| 변수 | α |
|---|---|
| 가중치 | 0, 0.3, 0.5, 1.0, 2.0 |

**관전 포인트** — α가 너무 크면 모든 로봇이 같은 우회로로 몰려
**혼잡이 이동할 뿐**인 현상이 나타날 수 있다.

---

### 실험 6 — 파이프라인 부하 한계

로봇 수를 올리며 **인프라 한계**를 찾는다. (알고리즘이 아닌 시스템 측정)

| 측정 | 한계 신호 |
|---|---|
| 시뮬레이터 틱 초과율 | 계산이 주기를 못 따라감 |
| Ingest p99 | 수신 지연 |
| 큐 적체 | 워커 처리량 부족 |
| 이벤트 적재 지연 | DB 쓰기 한계 |
| 이동 판단 p99 | Redis / FleetController 한계 |

**워커 pod 수를 바꿔 가며** 적체 해소 시점을 측정한다.
→ "워커 N개까지는 선형으로 처리량이 늘고, 그 이상은 DB가 병목"

## 결과 정리 형식

각 실험마다 아래를 남긴다.

```
실험 N — 제목
├── 가설
├── 조건 (고정 변수 / 조작 변수)
├── 결과 표
├── 그래프 (Grafana 스크린샷 또는 차트)
├── 해석
└── 결론 — 그래서 무엇을 알게 되었나
```

> **"예상과 달랐던 결과"를 반드시 기록한다.**
> 가설대로만 나온 실험은 설득력이 약하다. 예측이 빗나간 지점과
> 그 원인을 분석한 내용이 포트폴리오에서 가장 강한 부분이 된다.

## 대시보드 구성

### 운영 대시보드 (실시간)

| 패널 | 내용 |
|---|---|
| 맵 뷰 | 로봇 위치 실시간 (WebSocket) |
| 상태 분포 | Idle / Moving / Waiting / Working 비율 |
| 처리량 | 시간당 완료 작업 (추세) |
| 대기열 | Pending 작업 수 |
| 충돌 | 최근 발생 목록 |

### 분석 대시보드

| 패널 | 내용 |
|---|---|
| 로봇별 시간 분해 | 누적 막대 (Move/Work/Wait/Idle) |
| 혼잡 히트맵 | 맵 위 색상 |
| 경로 효율 분포 | 히스토그램 |
| 리드타임 | p50 / p90 / p99 |

### 시스템 대시보드

| 패널 | 내용 |
|---|---|
| pod 상태 | 개수, 재시작, CPU/메모리 |
| 파이프라인 | 수신률 / 처리율 / 적체 |
| 지연 | 이동 판단, 이벤트 적재 |
| 인프라 | RabbitMQ, Redis, PostgreSQL |
